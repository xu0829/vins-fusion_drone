在笔记本容器里跑通官方 VINS-Fusion

官方 VINS-Fusion 只有 ROS1（catkin）版本，所以路线是 Docker + Noetic 跑原版代码， 相机用 RealSense D430 的双目红外，IMU 从 PX4 飞控经 MAVLink 直读。下面是完整步骤、 每一步的实测数据，以及真正踩过的坑。

环境与硬件

动手前先核对这五项，任何一项对不上后面的参数都要重算。

宿主x86_64 笔记本 · Ubuntu 24.04 · ROS2 Jazzy（只当宿主，不参与）· 12 核
容器ros:noetic-ros-base，命名 vins_noetic，--net=host
算法官方 HKUST-Aerial-Robotics/VINS-Fusion（master，仅 ROS1）
相机Intel RealSense D430（8086:0ad4）· 只有双目红外，没有彩色流
飞控MicoAir743AIO · USB CDC-ACM 出 /dev/ttyACM0
标定~/drone/d430/calib_data/ 下 8 轮 Kalibr 结果，取 imu_cam_8
一个重要前提：标定不用重做。Kalibr 已经跑过 8 轮， 要做的是把它的输出翻译成 VINS-Fusion 的配置格式，而不是重新标定。 重标的精度天花板也已经量过：焦距差 2%、旋转差 1.3°、平移差 7 mm、时偏差 1 ms —— 这是单包标定的重复性，再标也收敛不了。

部署步骤

顺序有意义：容器要先直通设备，配置要在编译后生成，桥接要在 VINS 之前起来。

01

建容器并直通设备

用本地已有的 ros:noetic-ros-base 镜像，不 pull 新的（省磁盘）。相机和飞控都要直通进去。

docker run -itd --name vins_noetic --net=host \
  -v /dev/bus/usb:/dev/bus/usb \
  -v ~/xuqixuan_learning/vinsfusion:/root/vinsfusion \
  -v ~/drone/d430/calib_data:/root/calib_data \
  --device=/dev/video2 --device=/dev/video3 \
  --device=/dev/video4 --device=/dev/video5 \
  --device=/dev/ttyACM0 \
  --device-cgroup-rule='c 189:* rmw' \
  ros:noetic-ros-base sleep infinity

/dev/bus/usb 也挂进去，是因为 librealsense 走 USB 原始访问而不是 V4L2； 只给 /dev/video* 不够。

02

装依赖

Ceres 直接用 Noetic apt 里的 1.14.0，不必照官方 Dockerfile 从源码编 1.12 —— 省时省磁盘，且没有 API 不兼容问题。

apt-get update && apt-get install -y \
  libceres-dev libopencv-dev \
  ros-noetic-cv-bridge ros-noetic-image-transport \
  ros-noetic-message-filters ros-noetic-tf \
  ros-noetic-realsense2-camera ros-noetic-foxglove-bridge \
  python3-catkin-tools build-essential cmake
pip3 install pymavlink rosbags
03

克隆并编译 VINS-Fusion

cd /root && git clone https://github.com/HKUST-Aerial-Robotics/VINS-Fusion.git vinsfusion
mkdir -p /root/catkin_ws/src && cd /root/catkin_ws/src
ln -s /root/vinsfusion .
cd /root/catkin_ws && catkin build -DCMAKE_BUILD_TYPE=Release

源码在 /root/vinsfusion、构建产物在 /root/catkin_ws， 这个分离结构是为了让源码目录能整体 rsync 到别的机器。

Opencv4 兼容：Noetic 自带 OpenCV 4，官方代码里有一处 OpenCV 3 的写法需要打补丁， 见 tools/opencv4-compat.patch / apply_opencv4_compat.sh。
04

把 Kalibr 标定翻译成 VINS 配置

用 tools/kalibr2vins.py 生成三份文件到 config/d430_px4/。核心是两处换算：

VINS 字段来源注意
body_T_cam0/1inv(T_cam_imu)必须取逆。VINS 要的是 T_body_cam，Kalibr 给的是 T_cam_imu
tdtimeshift_cam_imu符号同 Kalibr，直接用
cam0/1.yamlintrinsics + distortionKalibr 的 radtan 正好 4 参数，一对一映射
格式陷阱：body_T_cam0 必须以 !!opencv-matrix 块（rows/cols/dt/data）输出。VINS 用 cv::FileStorage 读，写成普通嵌套列表会静默读成空。
05

启动相机

roslaunch realsense2_camera rs_camera.launch \
  enable_infra1:=true enable_infra2:=true \
  enable_color:=false enable_depth:=false \
  infra_width:=640 infra_height:=480 infra_fps:=30 \
  initial_reset:=true

分辨率必须是 640×480，和标定时的分辨率一致；enable_depth:=false 是因为 VINS 只用双目红外，开深度纯属浪费 USB 带宽。

ROS1 的参数名不是 ROS2 的。ROS1 是 infra_width / infra_height / infra_fps； ROS2 才是 depth_module.infra_profile。roslaunch 对未声明的参数不报错， 填错会静默退回默认的 848×480。
06

启动 IMU 桥接

不走 mavros，用 pymavlink 直读 HIGHRES_IMU（消息 ID 234），转成 /imu。

source /opt/ros/noetic/setup.bash
cd /root/vinsfusion/tools
IMU_CSV=/tmp/imu_raw.csv python3 -u px4_imu_node.py /dev/ttyACM0
  • 节点会发 MAV_CMD_SET_MESSAGE_INTERVAL 把 HIGHRES_IMU 往 200 Hz 拉。只在飞控内存生效，断电即恢复，不改固件。
  • PX4 的 IMU 是 FRD（x 前 / y 右 / z 下），必须翻成 FLU 再发。
  • ImuClockMapper(mode='slow') 把飞控时钟映射到宿主时钟。它报出的尺度是真的，别改成 lower 去锁死。
  • IMU_CSV 会把 sensor_time,arrival_time,stamp,scale_ppm 落盘，事后判时基问题靠它。
07

起 Foxglove 桥和界面

# 容器内
rosrun foxglove_bridge foxglove_bridge _port:=8767 _address:=0.0.0.0

# 宿主
bash tools/start_foxglove_vins.sh

布局文件 tools/foxglove_vins_layout.json，界面里「Import layout」导入后连 ws://127.0.0.1:8767，3D 面板固定坐标系设成 world。

端口分配：8765 = kswlt，8766 = d430_view（香橙派），8767 = 本机这套。

08

按顺序启动

顺序不能乱：相机要先把 USB 设备抓住，VINS 起来后是等图状态，等相机出图才初始化。

# 1. 相机（等约 20 秒，确认 640×480 / 30Hz）
# 2. IMU 桥接（约 3 秒，确认 /imu 有数）
# 3. vins_node
source /opt/ros/noetic/setup.bash
source /root/catkin_ws/devel/setup.bash
cd /root/vinsfusion
/root/catkin_ws/devel/.private/vins/lib/vins/vins_node \
    config/d430_px4/d430_px4_live_refnoise.yaml
容器里的后台进程陷阱：用 docker exec（不带 -d）起的后台进程， 会在 exec 的 shell 退出时一起被杀。要么加 -d，要么在一条命令里用 nohup … & 且不要马上退出。

踩过的坑

这一节是这份文档里最值钱的部分 —— 每一条都真金白银花过时间，而且大多静默失败，不查不知道。

我的锅：把 ROS2 的参数名喂给了 ROS1 自作自受

现象
相机重启后画面正常、频率正常，但 VINS 立刻发散 —— 因为分辨率从标的 640×480 变成了 848×480。
根因
我用了 depth_module.infra_profile:=640x480x30，那是 ROS2 版 realsense2_camera 的参数名。ROS1 的 launch 里根本没声明这个 arg，roslaunch 对未声明参数不报错，静默忽略。
教训
参数没生效不会报错。改任何参数后都要回读实际值确认（看日志里的 width/height，或直接查话题的分辨率），不能只看"命令跑通了"。

VINS 静止 120 秒后炸到 333 米 根因

现象
前 120 秒亚毫米级稳定、零警告，然后指数炸开：速度 0.87→2.49→6.67→17.7 m/s，每 13.34 秒翻 2.7 倍。
根因
配置里四个 IMU 噪声参数量级全错，直接来自 Kalibr 输出 —— Kalibr 没能估出它们（随机游走为 NaN，静止段只有 11.4 秒），留的是 PX4 datasheet 典型初值。
修法
换成官方 D435i 参考值。改后同一台设备静态跑 604.3 秒 / 9063 个位姿，最大位移 17 mm。
教训
"稳很久再炸"这个形态很容易被误读成时间轴缓慢累积误差。不要因为形状像累积误差就去怀疑时基。
参数官方 D435i 参考原值偏差
acc_n0.10.002540× 偏小
gyr_n0.010.00016959× 偏小
acc_w0.0010.00025× 偏小
gyr_w0.00015e-0620× 偏小

"34.7% 严重丢包" 是假警报 判据错误

现象
自己写的间隔检查脚本把 /imu 判成严重丢包，差点据此去改飞控参数、并放弃录标定包。
根因
脚本假设飞控以固定周期发送，把"长间隔不是基准的整数倍"当成丢包。但实测间隔只有 4506 µs 和 10513 µs 两档，10513 / 4506 = 7/3。而非整数倍恰恰证明不是丢包 —— 丢包只可能造出整数倍（4506 / 9012 / 13518）。
真相
1500 µs 是一个链路时隙：一条 HIGHRES_IMU（MAVLink v2 = 75 字节 = 750 bit）在 500 kbaud 下正好发 1500 µs。别的消息占了时隙，IMU 只能拿剩下的，于是周期在两档间跳。
正确判据
看 MAVLink 的 seq。实测 20205 条里只有 82 次不连续、洞大小全是 2 → 真丢包 0.40%。
又一个坑
seq 是每条链路一个全局计数器，不分消息类型。按消息类型分组去查连续性，会看到"每种消息都有洞"的假象（两条 HIGHRES_IMU 之间本来就插着几十条别的消息）。必须把所有消息合起来按到达顺序查。

相机卡死：进程活着，话题全静默 硬件/驱动

现象
相机进程正常、USB 树看着正常，但 /camera/* 没数据；VINS 卡在 waiting for image and imu...，/tf 和位姿跟着一起死。约 10 分钟复发一次。
线索
日志里上万条 control_transfer returned error ... Device or resource busy（librealsense 的 libusb 层）。设备号一路从 Dev 006 → 013 → 015 反复重新枚举 —— 典型的经过 USB hub 的症状。
排查结论
容器没有 CPU 限制，宿主 load 只有 1.22 / 12 核，CPU 饿死已排除。另外发现设备节点上 USB 自动挂起是开的（power/control=auto、autosuspend_delay_ms=2000），是另一个可疑诱因。
已做的处置
把相机 USB 从扩展坞拔下来直插笔记本端口（拓扑从 Bus002 → Hub → Dev015 变成 Bus002 → Dev019，中间无 hub，速度仍 5000M）。
状态
未验证。这个故障上次是约 10 分钟才复发，需要跑够 20–30 分钟才算数。

ROS1 僵尸注册：话题还在，但没有数据 ROS1

现象
节点被 kill -9 后，rosnode list / rostopic list 都还显示它，话题列得出来但永远没数据，rostopic hz 一直等。
修法
rosnode cleanup 清掉 master 里的死注册。判断真假可以查节点 URI 的端口是否真的在听。
教训
重启节点前先 rosnode cleanup，否则新节点会和一个幽灵抢同一个话题名。

我的锅：pkill -f 杀掉了自己的 shell 自作自受

现象
一条 pkill -f "[v]ins_node" 命令把自己所在的 shell 也杀了（退出码 143），后续命令全部没执行。
根因
方括号技巧确实避免了匹配 pkill 自己的进程名，但同一行里还有一句 echo "=== 杀掉旧 vins_node ===" —— 它的命令行里含字面量 vins_node，被正则匹配到了。 整个 shell 的命令行里只要出现这个字符串就会中招。
教训
杀进程尽量用 PID，不要用 pkill -f 配模式串；非要用，就确保整条命令行里不出现那个字面字符串。

排错时按带宽找大头

怀疑负载问题先看这个表，别凭感觉猜：

话题带宽备注
/camera/infra1/image_rect_raw9.53 MB/s绝对大头，两路约 19 MB/s
/imu61.3 KB/s

推论：要减负就动图像 —— 比如在 Foxglove 里关掉两个 Image 面板。 实测 Foxglove 自己会吃到 71% CPU，那才是真正的负载来源，不是 TF。

遗留问题

诚实列出还没解决的，避免后来者以为这套已经完美。

问题现状
相机卡死 已换到直插端口，效果未验证（原故障约 10 分钟复发，需观察更久）。USB 自动挂起仍是 auto，可用 echo on > /sys/bus/usb/devices/2-1/power/control 关掉（需 sudo，可逆，重启后恢复）。
IMU 速率不稳 实测 147–198 Hz 之间浮动，且周期不均匀（4506 / 10513 两档）。跑 VINS 够用，但不适合直接喂 imu_utils 做 Allan 方差标定 —— 标定假设等间隔采样。
IMU 噪声参数仍是借来的 用的是官方 D435i 参考值，不是本机实测。要真正的实测值，得先解决上面的速率问题，再录一段长静止包重算。
VINS 静止验证通过，真运动未验 604 秒静止漂 17 mm。手持运动、快速旋转下的表现还没测过。
容器 PID 1 是 sleep infinity 不回收僵尸进程，容器里会累积 defunct（只占 PID 槽，不影响功能）。只有重启容器能清。
基于 2026-09-27 的实测会话整理。所有频率、带宽、漂移数字均为当时实测值， 环境变化后需要重新测量。工具脚本位于 vinsfusion/tools/。
